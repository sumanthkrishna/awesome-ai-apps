# M03 — Sessions, memory and isolation

**APT Enterprise AI Lab** · 4 hours · Incremental stage 3/10

## Mission briefing
You inherit a working sample. Investigate its architecture before editing. Trace memory identity and persistence; demonstrate separate test sessions and prevent cross-session leakage.

## Verified upstream starting point
[`memory_agents/agno_memory_agent`](https://github.com/Arindam200/awesome-ai-apps/tree/main/memory_agents/agno_memory_agent) — an example to inspect and adapt, not a claim that this mission is already implemented in its code.

## Learning outcomes
1. Identify the entry point, inputs, outputs, model/tool boundary and dependencies.
2. Draw a request-to-response sequence diagram.
3. Modify the behavior safely, then reproduce a deliberate failure.
4. Add a repeatable test and document the root cause and tradeoffs.

## Inherit → investigate → modify → break → fix → defend
- **Inherit**: run the sample, capture setup commands, dependency versions and baseline output.
- **Investigate**: locate control flow and map data/trust boundaries.
- **Modify**: implement the scenario above with the smallest explainable change.
- **Break**: introduce a controlled failure in a disposable branch; preserve the original working behavior.
- **Fix**: use tests and evidence to establish recovery.
- **Defend**: describe alternatives, security, latency, cost and failure modes in a short technical review.

## Knowledge-base notes
**Input boundary:** where user or external data first enters. **Execution path:** the chain of calls from input to response. **Evidence:** logs, assertions, test cases and source references that support a conclusion. **Regression:** unintended loss of existing behavior after change.

## Learner deliverables
- `architecture.md` containing diagram, entry points and dependencies.
- `investigation.md` with observations, hypotheses and root-cause evidence.
- Test script, expected results and actual results.
- `decision-record.md` with alternatives and risk assessment.
- One-minute demo plus five-minute defense.

## Acceptance criteria
- Reproducible setup and baseline documented.
- Test cases cover success, invalid input and one failure.
- No secrets in commits, logs or screenshots.
- All claims supported by code inspection or a repeatable observation.
- A reviewer can reproduce the result independently.

## Instructor guidance
Provide the incident description first; withhold precise code locations. Increase hints only when learners cannot find the relevant boundary. Assess investigation, correctness, testing and defense—not merely screenshots of a running app.
